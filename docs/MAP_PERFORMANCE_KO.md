# 지도 범위·확대/축소·이동 성능 점검 (0.6.0)

국가 필터 없이 전 세계 OSM 지도·Nominatim 주소 검색·OSRM 자동차 경로를 사용합니다. 모든 나라·도로의 경로 제공, 실시간 교통 또는 상용 내비 수준의 정확도를 보장한다는 뜻은 아닙니다. 국가별 OSM 도로 데이터·차량 진입 가능 여부·공개 서버 상태에 따라 경로가 없을 수 있습니다.

## 실제 외부 서버 확인

6개 대륙, 7개 도시에서 실제 주소 검색과 자동차 경로 요청 14건 및 OSM 타일 1건이 HTTP 200을 반환했습니다. API 요청은 세션의 기존 프록시와 TLS 인증서 검증을 유지했습니다. 공개 장소 좌표를 사용했으며 실기기 GPS·실도로 주행 시험은 아닙니다.

| 도시 | 자동차 경로 거리 | 응답 시간 |
|---|---:|---:|
| Seoul Station South Korea | 4.01 km | 1.58초 |
| Paris France | 5.18 km | 1.55초 |
| New York USA | 2.15 km | 0.50초 |
| Tokyo Station Japan | 2.07 km | 0.45초 |
| Sao Paulo Brazil | 3.75 km | 0.99초 |
| Cape Town South Africa | 3.21 km | 0.42초 |
| Sydney Australia | 8.75 km | 0.35초 |

검색은 explicit submit 시에만 수행하고, 반복 검색은 캐시하며 공개 제공자 요청 간격을 제한합니다. 응답 시간은 이번 단일 관측값이며 SLA·최악 지연·항상 동일한 성능을 의미하지 않습니다. [원본 결과](validation/live-navigation-results.json).

## 확대·축소·이동

- 웹의 주변 지도와 내비 지도 모두 +/− 버튼, 휠, 드래그를 확인했습니다. 터치 에뮬레이션에서 두 손가락 벌리기·오므리기도 두 지도 모두 통과했습니다.
- 화면 크기가 바뀌거나 타이머가 갱신돼도 선택한 확대 배율을 유지합니다. 크기 변경 시 좌표 투영의 1 화면 픽셀 이내 반올림은 허용합니다.
- Android는 멀티터치 및 확대/축소 컨트롤을 사용합니다. 처음 GPS 위치 수신 시 지도를 그 위치로 맞추고 안내 시작 시 최소 줌 15의 거리 수준으로 복귀합니다. 주차 미리보기의 사용자 줌·이동은 GPS timestamp 갱신만으로 초기화하지 않습니다.
- 안내 중에는 기존 안전 정책대로 수동 지도 이동·확대/축소를 제한하고 위치를 자동 추적합니다. 정차 지도 조작 시험과 주행 중 버튼 잠금 시험은 구분합니다.

실제 서울 경로를 표시한 Chromium에서 버튼 확대·축소·드래그 후 보이는 타일이 모두 로드됐는지 확인했습니다. 지도 조작 전후 공유 엔진의 경로 좌표가 바뀌지 않는 것도 확인했습니다.

| 실제 지도 조작 → 타일 표시 완료 | 이번 관측 |
|---|---:|
| zoom in button and visible live tiles | 0.413초 |
| zoom out button and visible live tiles | 0.497초 |
| drag pan and visible live tiles | 0.403초 |

타일 요청은 화면 이동 중 불필요해지면 취소될 수 있습니다. 보이는 타일의 완전 로딩을 검사했으며, 화면 밖 타일을 미리 수집하지 않았습니다. 브라우저 테스트용 CA 등록은 기존 공개 OS 인증서만 사용했습니다. [실제 브라우저 기록](validation/live-browser-results.json).

## 찾아서 고친 성능 문제

- Android가 GPS fix마다 전체 Polyline·목적지·현재 위치 마커를 버리던 것을 고쳤습니다. 경로 객체는 경로 변경 시에만 만들고, GPS 갱신은 기존 마커 위치를 옮깁니다. 테마 변경도 선 객체를 다시 만들지 않습니다.
- 공통 경로 추적 엔진은 누적 거리의 이진 탐색으로 현재 위치에서 물리적으로 도달 가능한 구간만 투영합니다. 긴 단일 세그먼트·중복 좌표·날짜 변경선에서도 기존 거리·회전 판정을 유지하는지 검사했습니다.
- 웹은 고정 GPS·타이머 갱신마다 중심 이동을 반복하지 않습니다. 안내 문구의 텍스트만 바꾸어 종료 버튼 포커스·DOM 객체를 유지합니다.
- 창 크기 변경 시 확대 배율을 덮어쓰던 fitBounds를 제거했습니다. 지도 ResizeObserver는 화면 종료 시 disconnect하고, 같은 스타일의 지도 필터는 다시 적용하지 않습니다.

## 고정 부하 성능 비교

동일한 headless Chromium, 동일한 100,000개 지점의 합성 직선 경로, 120회 GPS 갱신, CDP CPU 4배 감속 조건입니다. 지도 타일 요청은 이 CPU 시험에서 차단했으며 실제 서버 지연 시험과 구분합니다. 이 수치는 실기기 화면 FPS가 아닙니다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| GPS 처리 + 렌더 갱신 p50 | 29.4ms | 5.8ms |
| GPS 처리 + 렌더 갱신 p95 | 34.4ms | 9.3ms |
| 갱신 최대값 | 58.6ms | 11.7ms |
| 고정 위치 25회 갱신 중 불필요한 중심 이동 | 25회 | 0회 |
| 같은 25회 중 안내 DOM 자식 재생성 | 25회 | 0회 |
| 종료 버튼 객체 유지 | 실패 | 통과 |

이번 수정 후에도 100,000개 지점의 매우 큰 경로를 처음 파싱하고 표시하는 데 약 1.03초가 걸렸습니다(4배 CPU 감속). 경로 수신·초기 표시 비용을 숨기거나 모든 화면이 끊김 없다고 주장하지 않습니다. 작은 도시 경로와 이 합성 스트레스 경로는 별도입니다.

[수정 전 기록](validation/map-performance-baseline.json) · [수정 후 기록](validation/map-performance-results.json). Android는 Robolectric에서 50,001개 지점의 선 객체를 100회 GPS 갱신 뒤에도 재사용하고, 경로 교체·GPS 중단·줌·중심 유지가 작동하는지 검사했습니다. 실제 APK의 저사양 기기·Pleos 디스플레이 FPS, 장시간 발열·주행·열악한 통신 상태의 체감 성능은 미검증입니다.

## 재현

```bash
./scripts/build-web.sh

# 별도 셸에서
node scripts/web/verify-map-performance.cjs
python3 scripts/check-navigation-live.py --all-regions
```

기본 CI는 CPU 1배의 결정적 지도 검사 8개를 기존 브라우저 검사와 함께 수행합니다. 외부 서버 확인은 의도적으로 CI fixture와 구분합니다.

## 0.7.0 가게 검색 추가 후 회귀

같은 10만 지점/120개 GPS/CPU 4배 감속 검사 8개가 통과했습니다. 초기 파싱·표시는 약 1.30초, GPS 처리·렌더 갱신 p95 11.6ms, 최대 25.5ms였습니다. [별도 결과](validation/map-performance-v070.json). 위 0.6.0 전후 비교와 구분하며, 실기기·실차 FPS를 뜻하지 않습니다. 가게 검색·경로의 실제 표본과 실패 사례는 [가게 검색 안내](PLACE_SEARCH_KO.md)에 있습니다.


0.8.0의 요청 취소·최신 GPS로 재계산·복귀/오류 문구 보완과 초기 경로 처리 개선은 [세부 재점검](DETAIL_REVIEW_KO.md)에 기록했습니다. 기존 0.6/0.7 성능 관측은 해당 버전의 과거 근거입니다.
